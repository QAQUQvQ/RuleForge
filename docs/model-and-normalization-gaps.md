# RuleForge 标准化与领域模型缺口说明
核查日期：2026-10-12。下文保留 M1+ 实施前的差距记录。当前已补齐通用来源、分型装备、五类记录、离线抽取、审核发布和 v2 迁移；实际范围与剩余项见 [M1+ 报告](m1-enhancement-report.md)。

## 当前已经完成的边界
403 页官方 PDF 已由 xParse 真实解析；原始响应包括段落、标题、表格、页码和坐标。
标准化程序目前只识别 Leather 护甲表行、Light Armor 说明、属性调整值说明。
数据库只有 srd51.ac.leather v1 一条已验证规则和相应三处来源。
47 项测试覆盖当前闭环和安全/异常路径，不代表所有 SRD 规则通过测试。

## 标准化缺口
“解析”得到文档结构；“标准化”还要将条目变为统一、可验证、可引用的游戏数据。
皮甲示例：原始表格 Leather / 11+Dex modifier -> 稳定装备 ID、轻甲类别、基础 AC 11、属性 dexterity、来源、审核状态 -> 安全 DSL。
当前皮甲采用专用规则路径，尚无完整 Item 实例与装备目录。
- 护甲：缺全部装备记录、AC 模式、敏捷上限、力量要求、隐匿影响、价格/重量单位归一。
- 武器：缺伤害骰和类型、射程、属性、熟练分类、单双手使用模式等数据。
- 职业表：缺职业定义、按等级的熟练/特性/资源进展、特性引用；尚未处理表格合并单元格与跨页表的一般情形。
- 状态：缺稳定状态 ID、子效果、适用对象、触发/结束条件、相互关系；当前角色 conditions 是自由字符串。
- 战斗：缺规则条目索引、触发时机、前置条件、资源消耗和效果的统一表达。
- 通用能力：缺批量标准化、逐字段证据、去重、别名、完整性统计、OCR 异常报告、人工复核队列与发布流程。
复杂条目可先以有来源的知识条目保存并标注“仅检索”；不需要把全文全部编译成可执行逻辑。

## Schema 缺口
- RuleDSL：id 固定为 srd51.ac.leather，version 固定 1，ruleset 固定 srd-5.1，category 固定 armor_class；只有 const/ability_modifier/add。尚不能表示攻击、伤害、状态、法术或 Homebrew。
- RuleRecord：来源数固定为 3。SourceSpan.role 固定为三种皮甲证据角色；引用格式限定 /data/elements/N/text。它是首条规则专用结构，不是通用规则/引用模型。
- Item：仅 id/name/ruleset/category/source_ids/review_status。没有护甲或武器的实际数值字段。数据库没有装备目录表。
- Character：有六维、总等级、HP、速度及简单装备。缺职业/种族/背景引用、技能/豁免熟练、库存与实际装备 ID、职业特性、资源当前/最大值和恢复规则等。法术相关字段后续按支持范围加入。
- Creature：继承 Character 再加 kind，因此仍受玩家等级等字段限制。缺适合怪物的挑战等级、类型、体型、感官、抗性/免疫、动作等结构。
- CombatState：有阶段、先攻、当前行动者、行动额度、反应窗口和简单持续效果。缺死亡豁免、稳定/死亡、专注、结构化状态实例，以及具体效果上下文与结算信息。
- 命令/事件：已有部分命令。事件有类型、骰值、规则来源和前后哈希，但缺各事件专用载荷；例如 moved 没有目的位置字段，attack_resolved 没有目标/伤害变化字段，不能仅靠这些事件重放战斗。
Schema 负责表达与验证数据，状态机负责推进与结算；有 Schema 不代表攻击或回合流程已经实现。

## 如何影响后续功能
目前能证明皮甲 AC 的真实来源和计算结果，不能靠更换输入直接处理链甲、武器攻击、职业升级或状态效果。
单纯放开字段限制也不能完成扩展：必须同时补齐来源、类型、编译器白名单、适用性校验及测试。

## 分阶段补齐边界
M1 加强：建立通用 Rule/SourceReference、分型 Item、职业/状态知识条目模型；对护甲、武器、职业表、状态和战斗章节形成可追溯标准化记录；未支持计算的条目标注为仅检索；报告数量、失败和待复核情况。
M2：角色创建所需领域字段与装备选择、熟练和派生数值；实现基础攻击、伤害。
M3：战斗命令处理、时机、状态、资源、结构化事件、事务一致性与重放。
M4：Homebrew 独立命名空间、审核发布和受限执行模板。
不将整个 SRD 的全部特殊规则自动化作为 M1 或 V1 的前提；每项能力应有明确支持范围和对应测试。
